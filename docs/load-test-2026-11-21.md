## AI/RAG 流式问答（mock 模型）

为了验证 Chat/RAG 链路而不消耗外部 API 预算，新增了 OpenAI 兼容的本地 mock 模型：

- `scripts/mock-ai.mjs`：`/chat/completions`（含 SSE）、`/embeddings`、`/rerank`
- `deploy/docker-compose.loadtest.yml`：mock 服务 + user-api 压测环境
- `scripts/load-test-chat.mjs`：登录后并发请求 `/chat/stream`，解析 `usage/done/error` 事件

环境：Docker + Caddy HTTPS，`ALL` 范围，6 篇资料，`AI_ENABLED=true`，`EMBEDDING_PROVIDER=dev`，关闭 rerank，mock 流式返回约 4 段文本。

| 指标 | 结果 |
|---|---:|
| 并发 | 10 VUs / 15s |
| 请求 | 229 |
| 成功 | 229 |
| 失败 | 0 |
| RPS | 15.27 |
| P50 | 606.5 ms |
| P95 | 1111.4 ms |
| P99 | 1186.6 ms |
| 最大 | 1247.6 ms |
| Prompt tokens | 360,718 |
| Completion tokens | 4,351 |
| 总 tokens | 365,069 |
| 服务端记录延迟 | 平均 118.4 ms，最大 526 ms |

说明：

- `ai_usage` 记录 811 次调用全部 `SUCCESS`（805 CHAT + 6 EMBEDDING），805 条助手消息和 6,440 条引用落库。
- 客户端 P50 与服务端记录延迟的差值主要来自流结束后的 MySQL 写入（助手消息、引用、用量、会话更新）和代理链路；当前实现是在发送 `done` 前同步落库。
- 压测中发现流式问答线程池默认只有 4 个线程，10 并发会排队。已改成可配置，默认 core=16 / max=32 / queue=100（`CHAT_EXECUTOR_*`）。
- mock 模型只验证链路、并发和资源使用，不代表真实 DeepSeek 的延迟、限流和回答质量；dev embedding 也不是语义向量。
- 全站月度 token 预算默认 2M，本轮压测消耗约 1.29M（含前几轮调试），因此没有继续加大并发。
- 复现：

```powershell
$env:DOMAIN='localhost'
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.https.yml `
  -f deploy/docker-compose.loadtest.yml up -d --build

$env:NODE_TLS_REJECT_UNAUTHORIZED='0'
$env:BASE_URL='https://localhost/api/v1'
$env:EMAIL='chatload@shiye.local'
$env:PASSWORD='ChatLoad123'
$env:VUS='10'
$env:DURATION='15s'
node scripts/load-test-chat.mjs
```

> 压测用户和 mock 服务只用于本地验证；生产不要启用 `docker-compose.loadtest.yml`。
