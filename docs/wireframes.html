RAG 切片策略：按段落还是按固定长度？

来源：example.com/rag-chunking 2026-11-08 1,842 字

AI 摘要

  • 固定长度切片实现简单，但容易把一句话切断；中文长文更推荐按标题 + 段落切。
  • 推荐单块 500~800 字，重叠 10%~15%；chunk 大小要和 embedding 模型、topK 一起调。
  • 切片不是越小越好：太小会丢上下文，太大会稀释检索命中率。
正文切片（24）元数据

做 RAG 时，切片策略往往比换模型更影响最终效果。很多教程直接给一个固定长度，但在中文长文里，这样做很容易把一个小节拆成两半。

chunk #03 · 612 字

一种更稳的做法是先按标题层级切一级：每个二级标题下的内容作为一个候选块；如果超过 800 字，再在段内按句子边界做二次切分。

重叠的作用是防止答案正好落在切口附近。10%~15% 是一个经验值，但并不是硬性规定。

另一种观点认为，切片大小应该由问题和文档类型决定。FAQ、代码、论文的合理切法并不相同，不能用一个参数打天下。

chunk #04 · 588 字

如果检索效果不好，先看切片是否完整，再看 embedding 模型，最后才考虑 rerank。顺序反了会浪费很多时间。

最后，切片要保存原文位置（charStart / charEnd），否则问答里的引用无法跳回原文，用户就不会信任你的答案。

实现说明
  • 摘要是锦上添花，切片和原文定位才是核心。不要花太多时间在“摘要好不好看”上。
  • 每个切片必须保存 articleId / chunkIndex / charStart / charEnd，引用才能跳回原文。
  • “重新解析”会重建切片和向量，要保证幂等：同一篇文章重复解析不能产生重复切片。
  • “与本文对话”= 把检索范围限定为单篇，适合长文精读。

AI

你收藏的资料里主要有三种倾向：

1. 按语义段落切，单块 500~800 字，重叠 10%~15%。 这是最常见的中文长文方案，重点是不要把一句话切断。[1]

实现说明
  • 本质是 content script 往每个页面注入一个固定定位的容器，用 Shadow DOM 隔离样式；点球时再挂载 Vue 面板。
  • 三种模式：资料库（RAG + 引用）、当前页面（临时上下文，不一定要收藏）、通用（不检索，直接问模型）。默认资料库。
  • 浮动球用 position: fixed + z-index: 2147483647；拖动位置存 chrome.storage.local，下次记住。
  • 当前页内容由 content script 读取：title、URL、选中文本、Readability 正文；提问时一起发给后端。
  • 登录：网页端登录后生成一次性 code，插件换 token；token 存 chrome.storage.local，不要存密码。
  • MV3 不允许执行远程 JS：Vue 代码必须打包进插件；可以请求后端 API，但不能从 CDN 拉脚本执行。
  • 不是所有页面都能注入：chrome://、扩展商店、PDF 内置阅读器等会被浏览器禁止，属于正常现象。
  • 自己用不用“上传”：chrome://extensions → 开发者模式 → 加载已解压；发给朋友就打包 zip。
  • 公开上架才麻烦：Chrome Web Store 一次性 $5 + 隐私政策 + 审核；Edge Add-ons 免费，国内更省事。

实现说明
  • 插件用 chrome.bookmarks.getSubTree(folderId) 递归读取文件夹；这段逻辑放在 background service worker，面板通过 sendMessage 拿数据。
  • 只把 URL + 标题发给后端，正文由后端抓取；不要试图在插件里批量打开所有书签，慢且容易被封。

  • 书签变更监听：chrome.bookmarks.onCreated / onRemoved，新增链接可以自动入队；删除只标记归档，不自动删资料。
  • 先限制一个文件夹、最多 50 条，跑通再放开；不要第一次就导入几千条。
  • 权限 bookmarks 比较敏感，上架时审核会问用途；自己用加载已解压不受影响。
